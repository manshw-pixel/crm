# Lead Role Implementation Plan (PR 3 of 3)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `lead` role. Admins assign one Lead per account (`account.leadId` = the Lead's profile id). A Lead without Finance access can see and work only on accounts where they are the Lead — enforced by Postgres RLS on every account-linked table and storage bucket. A Lead with Finance access sees everything.

**Architecture:** Two SQL helpers decide visibility once per query: `lead_restricted()` (caller is an active `lead` without `finance`) and `lead_owns(org, account_id)` (that account's `data->>'leadId'` is the caller). Every existing account-linked SELECT/INSERT/UPDATE/DELETE policy gains `and (not (select public.lead_restricted()) or <ownership check>)`, so admins, CSMs and finance users take a cheap short-circuit and their behaviour is unchanged. Leads are blocked from CREATING accounts in the existing `guard_account_owner` trigger, never in the INSERT policy (see Global Constraints). The client adds the role to user management, a Lead picker in Edit account, and hides account-creation UI for Leads; data narrowing needs no client code because the store only holds what RLS returns.

**Tech Stack:** Postgres/Supabase SQL (`supabase-setup.sql`, `finance.sql`), React globals in `src/NN-*.jsx`, RLS harness `tests/rls` (CI job `rls`; there is NO local Docker on the dev machine — RLS tests are verified only in CI on a draft PR), Playwright E2E `tests/health`.

**Spec:** `docs/superpowers/specs/2026-10-13-custom-fields-ownership-leads-design.md` (section "PR 3").

## Global Constraints

- Role values exactly: `'admin' | 'user' | 'lead'`.
- `leadId` stores the Lead's `profiles.id` (uuid text), never a name.
- Visibility rule: caller sees an account iff caller is active in the org AND (`role <> 'lead'` OR `finance` OR `accounts.data->>'leadId' = auth.uid()::text`).
- Child rows (contacts/activities/tasks/opportunities) belong to `data->>'accountId'`. A child row with blank `accountId` is visible to a restricted Lead only if `data->>'owner'` equals the Lead's `profiles.name`.
- **`merge_row` writes every edit as `insert … on conflict do update`. Postgres checks the INSERT policy's WITH CHECK on the proposed row even when it ends up updating — so NEVER add "leads can't insert" to an INSERT policy (it would block every Lead edit).** Block Lead account creation in `guard_account_owner`'s INSERT branch (new id only).
- Leads (any finance flag) cannot create or delete accounts, cannot change `csm`/`csmSince`/`leadId` (already enforced by `guard_account_owner` for non-admins), and do not get Settings (already admin-only).
- Policies wrap helpers as `(select public.fn())` like every existing policy, so they run once per query.
- Every RLS assertion of "cannot see" is paired with a positive control on the same session ("can see own") — see memory note on vacuous absence tests.
- New RLS test files: `import` in `tests/rls/run.mjs` BEFORE `migration.test.mjs`. New E2E files: `import` in `tests/health/run.mjs`.
- `supabase-setup.sql` and `finance.sql` must stay idempotent (re-runnable); the user re-runs both after merge.
- The repo's `supabase-setup.sql` has unrelated uncommitted local edits by the user — stage only your own hunks (`git add -p`).

## Review Focus

1. **A Lead editing their own account (e.g. ARR)** must succeed through `merge_row`'s upsert — the INSERT policy must not reject it. (Task 1 RLS test "lead edits own account".)
2. **A Lead with Finance access** sees every account, invoice and PO — the override must apply in every policy, not just accounts. (Task 1 + Task 2 RLS tests.)
3. **A task with no account owned by the Lead** is visible; one owned by someone else is not. (Task 1 RLS test.)
4. **Invoice PDFs** (path `<org>/<invoice id>.pdf`, no account id in the path) — a restricted Lead can read only PDFs of their accounts' invoices. (Task 2 RLS test.)
5. **An admin demoting a Lead to user / promoting to lead** via the Users card works, and the role shows in the badge; the last-admin guard still holds. (Task 3 E2E.)

    ```sql
    $$ select exists (select 1 from profiles where id = auth.uid() and role = 'lead' and not finance and not disabled) $$;
    create or replace function public.lead_owns(p_org uuid, p_account text)
    returns boolean language sql stable security definer set search_path = public as
    ```

```js
// Lead role (spec 2026-10-13 PR 3). Every "cannot" is paired with a "can" on the same session.
import { test, assert } from "../health/framework.mjs";
import { sessions, sql, ORG_A, invitedFresh, seedRow } from "./fixtures.mjs";

let lead = null;   // { client, id } — a restricted lead in org A
const mkLead = async () => {
  if (lead) return lead;
  lead = await invitedFresh("lead1@test.local");
  await sql(`update profiles set role = 'lead', name = 'Lead One' where id = $1`, [lead.id]);
  return lead;
};
const ids = async (client, table) => ((await client.from(table).select("id")).data || []).map(r => r.id).sort();
const merge = (client, tbl, row_id, patch) => client.rpc("merge_row", { tbl, row_id, patch, appends: {} });
const clean = () => sql(`delete from public.accounts where id like 'ld-%'; delete from public.contacts where id like 'ld-%';
  delete from public.tasks where id like 'ld-%'; delete from public.activities where id like 'ld-%'; delete from public.opportunities where id like 'ld-%'`);

async function world(l) {
  await seedRow("accounts", "ld-mine", { name: "Mine", leadId: l.id });
  await seedRow("accounts", "ld-other", { name: "Other" });
  await seedRow("contacts", "ld-c-mine", { accountId: "ld-mine", name: "A" });
  await seedRow("contacts", "ld-c-other", { accountId: "ld-other", name: "B" });
  await seedRow("tasks", "ld-t-own", { title: "no account, mine", owner: "Lead One" });
  await seedRow("tasks", "ld-t-else", { title: "no account, theirs", owner: "Admin User" });
}

test("a restricted lead sees only their accounts and those accounts' children", async () => {
  const l = await mkLead();
  try {
    await world(l);
    const acc = (await ids(l.client, "accounts")).filter(i => i.startsWith("ld-"));
    assert(JSON.stringify(acc) === '["ld-mine"]', "lead accounts: " + JSON.stringify(acc));
    const con = (await ids(l.client, "contacts")).filter(i => i.startsWith("ld-"));
    assert(JSON.stringify(con) === '["ld-c-mine"]', "lead contacts: " + JSON.stringify(con));
    const tk = (await ids(l.client, "tasks")).filter(i => i.startsWith("ld-"));
    assert(JSON.stringify(tk) === '["ld-t-own"]', "lead tasks: " + JSON.stringify(tk));
    const userSees = (await ids(sessions.user, "accounts")).filter(i => i.startsWith("ld-"));
    assert(userSees.length === 2, "control: a CSM must still see every account: " + JSON.stringify(userSees));
  } finally { await clean(); }
});

test("lead edits own account; cannot edit, create or re-point others", async () => {
  const l = await mkLead();
  try {
    await world(l);
    const ok = await merge(l.client, "accounts", "ld-mine", { arr: 5 });
    assert(!ok.error, "lead edit of own account failed: " + ok.error?.message);
    const other = await merge(l.client, "accounts", "ld-other", { arr: 5 });
    assert(other.error, "lead edited an account they cannot see");
    const created = await merge(l.client, "accounts", "ld-new", { name: "New" });
    assert(created.error && /Leads cannot create accounts/.test(created.error.message), "lead created an account: " + JSON.stringify(created));
    const child = await merge(l.client, "contacts", "ld-c-new", { accountId: "ld-other", name: "X" });
    assert(child.error, "lead attached a contact to an invisible account");
    const childOk = await merge(l.client, "contacts", "ld-c-new2", { accountId: "ld-mine", name: "Y" });
    assert(!childOk.error, "control: lead adding a contact to own account failed: " + childOk.error?.message);
  } finally { await clean(); }
});

test("a lead with finance access sees every account", async () => {
  const l = await mkLead();
  try {
    await world(l);
    await sql(`update profiles set finance = true where id = $1`, [l.id]);
    const acc = (await ids(l.client, "accounts")).filter(i => i.startsWith("ld-"));
    assert(acc.length === 2, "finance lead accounts: " + JSON.stringify(acc));
  } finally { await sql(`update profiles set finance = false where id = $1`, [lead.id]); await clean(); }
});

test("invite_user accepts the lead role", async () => {
  const r = await sessions.admin.rpc("invite_user", { p_email: "lead-invite@test.local", p_role: "lead" });
  try { assert(!r.error, "invite as lead failed: " + r.error?.message); }
  finally { await sql(`delete from invites where email = 'lead-invite@test.local'`); }
});
```
